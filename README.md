# Сводка поддержки Руссмаркет

Демо решения тестового задания: как превратить четыре записи CRM и связанные
сообщения в проверяемый список действий для сотрудника support.

**Демо:** https://demo.balkhaev.com  
**Код:** https://github.com/balkhaev/demo-test

## Что показывает решение

Система отделяет сведения в переписке от подтверждений в CRM, обнаруживает
расхождения и объясняет приоритет. Оператор видит исходные факты, сработавшее
правило, недостающие подтверждения и следующий шаг. Сообщение сотрудника не
считается согласованием руководителя, а сообщение курьера «не раньше 13:00»
не становится обещанием доставки ровно в 13:00.

Расчёт выполняет настоящий Node.js backend. Интерфейс отправляет собственный
снимок данных на сервер и показывает его ответ. Правила не зависят от браузера,
сети, LLM или текущих часов: время оценки передаётся явно в `asOf`.

## Посмотреть за три минуты

1. Откройте сводку. Сопоставьте CRM, сообщение и действие для П-08 и С-24.
   Проверьте фильтры: срочная доставка, задачи на сегодня, завершённый случай.
2. Откройте подробную страницу П-08. Проследите путь от источников к решению:
   какое правило сработало, что неизвестно и какие факты нужны для закрытия.
3. Измените демо-сценарий на странице случая и пересчитайте сводку. Например,
   принятие документов снимает препятствие для С-17; сообщение о недостаче
   требует проверки даже после отмеченной приёмки.
4. В разделе бизнес-логики прочитайте короткий псевдокод всего процесса.
   Поставка, приём, увольнение, сроки и проверка данных — отдельные разделы
   с условиями «если → то». Ссылка из решения выделяет нужное правило.
   Кнопка «Проверить на случае» открывает интерактивный сценарий, а вкладка
   «Исходник JavaScript» — соответствующий исполняемый модуль сервера.
   Условия, приоритеты, действия и проверки генерируются из исполняемых
   определений; отдельной ручной копии правил в браузере нет.
   Псевдокод и JavaScript подсвечены. У каждой ветки есть ссылка на строки
   GitHub, у исходника — ссылки на отдельные строки.

## Устройство

| Файл | Ответственность |
| --- | --- |
| `domain/rules.js` | Оценка случая: проверка времени источников → первое подходящее правило → объяснение |
| `domain/rules/` | Единые определения правил поставки, приёма, увольнения, дат источников и приоритета |
| `domain/expressions.js` | Выражения условий: один набор операций для исполнения и отображения |
| `domain/rule-engine.js` | Первое совпадение, получение результата и описание определения |
| `domain/deadlines.js`, `domain/dates.js` | Применение правил срока, даты и форматирование по Москве |
| `domain/evidence.js` | Подтверждения, порядок событий и неизвестные факты |
| `domain/decision.js` | Единая структура решения: приоритет, причина, проверка, действие, условия закрытия |
| `domain/validation.js` | Контракт снимка, типы, допустимые значения, даты и уникальность ID |
| `domain/brief-service.js` | Сценарий приложения: валидация → независимый снимок → правила → счётчики |
| `fixtures/demo.js` | Четыре вымышленных случая и фиксированное время демонстрации |
| `server/http.js` | HTTP-граница, ограничения запросов, раздача интерфейса и разрешённых исходников |
| `prompts/extract-facts.txt` | Контракт извлечения фактов из свободного текста для будущей интеграции с LLM |
| `test/engine.test.mjs` | Бизнес-сценарии, противоречия, неизвестные факты и временные границы |
| `test/http.test.mjs` | Проверки API, изоляции посетителей, ошибок входа и выдачи файлов |
| `test/logic-guide.test.mjs` | Полнота и порядок объяснений, прямые ссылки и безопасная обработка адресов |
| `test/production.test.mjs` | Запуск состава Docker-образа без DevHub, в том числе с унаследованными переменными |
| `server/logic-guide.js` | Генерация страницы правил из тех же определений, что использует расчёт |
| `server/source-files.js` | Разрешённые исходники, диапазоны строк и ссылки GitHub |
| `dist/logic-guide.js`, `dist/highlight.js` | Форматирование полученного псевдокода и безопасная подсветка |
| `dist/logic-view.js` | Страница логики: разделы, выделение правила и отдельный просмотр исходников |
| `dist/` | Интерфейс: сводка, подробности случая, сценарии и просмотр бизнес-кода |

Один HTTP-процесс, без фреймворка, runtime-зависимостей, базы и очереди.
Для четырёх демонстрационных случаев этого достаточно. Хранение, авторизация,
адаптеры CRM и фоновые задания появляются только при переходе к реальной интеграции.

Правило задаётся один раз: `when` — дерево выражений (`eq`, `all`, `not`,
`before`), `then` — приоритет, причина, проверка, действие и условия закрытия.
Сервер исполняет `when`, а генератор превращает то же дерево в русскую запись.
Тексты действий и проверок берутся непосредственно из `then`. Контекстная
причина вычисляется только для выбранного правила и видна в карточке случая.
Порядок массивов определяет и исполнение, и порядок веток на странице.
`deadline` ссылается на общий набор правил срока.

Версия правил вычисляется из их определений автоматически. При пересчёте
на новой версии интерфейс обновляет описание и кеш исходников. В production
ссылки GitHub закреплены за `SOURCE_COMMIT`, который передаёт Coolify:
последующие изменения `main` не сдвигают строки этих ссылок. Локально без
этой переменной ссылки ведут на `main`. Приватный репозиторий требует доступа
в GitHub; страница просмотра исходников в самом демо доступна как прежде.

## Контракт API

| Метод | Адрес | Результат |
| --- | --- | --- |
| GET | `/api/health` | `{ "status": "ok" }` |
| GET | `/api/demo` | Исходный снимок, время оценки, серверная сводка и счётчики |
| POST | `/api/evaluate` | Пересчёт переданного `{ asOf, cases }` |
| GET | `/api/logic` | `{ topics, rulesVersion, revision }`: псевдокод и ссылки из исполняемых определений |
| GET | `/api/source/:key` | `{ path, language, content, githubUrl, revision }`; разрешённые ключи перечислены в `server/source-files.js` |

Ответ расчёта:

```json
{
  "asOf": "2026-10-19T10:00:00+03:00",
  "cases": [],
  "summary": [],
  "counts": { "total": 0, "attention": 0, "done": 0, "urgent": 0 },
  "rulesVersion": "..."
}
```

`GET /api/demo` дополнительно возвращает `snapshot: { label, date }`.
Каждый элемент `summary` содержит исходные сведения и решение: `priority`,
`needsAttention`, `statusLabel`, `reason`, `check`, `action`, а также
структурированное объяснение правила. Точные поля описаны исполняемым кодом
`domain/rules.js`.

Снимок содержит не более 50 случаев. Поля и перечисления проверяются строго,
булевы значения не приводятся из строк. Неизвестный бизнес-факт передаётся как
`null`; он не означает подтверждение. Временные метки требуют часового пояса,
даты проверяются на существование, ID случаев должны быть уникальны.
Время из исходного задания не выдумывается: неизвестные даты сообщений остаются
неизвестными и видны в объяснении решения.

Ошибка в данных возвращает HTTP 422:

```json
{
  "error": {
    "code": "INVALID_FIELD",
    "message": "Ожидается true, false или null.",
    "fields": [
      { "path": "cases[1].crm.managerApproved", "message": "Ожидается true, false или null." }
    ]
  }
}
```

Невалидный JSON возвращает 400, неверный Content-Type — 415, запрос больше
64 КиБ — 413. Неизвестные маршруты и непубличные исходники недоступны.
API и HTML не кешируются; версии CSS и JavaScript имеют отдельные адреса.

## Проверить и запустить

Требуется Node.js 22 или новее. Устанавливать зависимости не нужно.

```sh
npm run check
npm start
```

`npm run check` проверяет синтаксис и запускает доменные и HTTP-тесты.
HTTP-тесты поднимают собственный сервер на свободном порту и закрывают его после
проверки. Они подтверждают, что изменение снимка одного посетителя не меняет
исходные данные другого, ошибки имеют понятный контракт, а произвольные файлы
проекта не выдаются наружу.
Тесты генератора временно меняют условие, действие и приоритет и проверяют,
что одновременно меняются реальный расчёт и страница. Они также проверяют
порядок веток, точность ссылок на строки и экранирование HTML в подсветке.

Production entrypoint — `node server/http.js`, порт задаётся через `PORT`
(по умолчанию 80). В Docker используется Node.js 24 Alpine, непривилегированный
пользователь `node`, порт 80 и проверка `/api/health`. Контейнер не пишет
на диск и не требует внешних сервисов. В Coolify достаточно Dockerfile-сборки
и домена `https://demo.balkhaev.com`.

На рабочей машине владельца локальные dev-сервисы запускаются только через DevHub;
`npm start` остаётся самостоятельной production-командой контейнера.

Проект подключён через `devhub.json`: `bun F:/code/devhub/src/cli.ts start demo-test/site`.
Локальный адрес — `http://127.0.0.1:4176/#/logic`. Политика `.devhub/worktree.json`
задаёт режим MVP, проверки и публикацию. После проверки `main` команда
`bun F:/code/devhub/src/stage.ts publish --project F:/code/demo-test` отправляет
коммиты в GitHub и запускает `scripts/deploy.mjs`. Скрипт использует
`COOLIFY_ACCESS_TOKEN`, проверяет целевое приложение, дожидается выпуска нужного
коммита и сверяет опубликованные файлы с ним.

## Границы и переход к рабочему процессу

- Источники вымышленные. Фиксированный понедельник 19 октября 2026 года выбран
  для воспроизводимости; в исходном задании календарной даты нет.
- CRM, чаты и LLM не подключены. Сигналы сообщений размечены заранее.
  Изменение свободного текста само по себе не извлекает новые факты.
- Сервер не хранит общую сессию. Каждый запрос вычисляет результат только для
  переданного снимка; изменения не переживают сброс/перезагрузку демо.
- Рекомендация не выполняет действие: нет автоматической записи в CRM,
  отправки сообщений, подтверждения документов или завершения увольнения.
- Условие закрытия означает достаточность представленных фактов в пределах
  правила, а не полноту кадрового или логистического регламента.

Первый рабочий запуск: разрешённая выгрузка CRM и связанных сообщений, сопоставление
по ID и сохранение ссылки на каждый источник. Несопоставленные и неоднозначные
данные идут на ручную проверку. Правила и качество извлечения проверяются вместе
с support-командой на реальных примерах. Первую неделю сводку сравнивают с ручной
работой: пропуски срочных случаев, лишние задачи и время подготовки. Заявлять
экономию времени можно только после этого измерения.
